Cryptography
The technology that keeps data private and proves who sent it. It is behind the padlock in your browser, your bank card, and almost every login.
Post-quantum cryptography
Newer cryptography built to stay secure even against a quantum computer. Often shortened to PQC.
Q-Day
The hypothetical day a quantum computer becomes able to break the cryptography protecting the internet today. Nobody knows when that is, and this tool does not try to guess.
Crypto agility
Being able to find, manage and replace cryptography without rebuilding the whole organization. The question is not what you use today, but how fast you could change it.

      So what actually helps?

      Three things stopped this response: a supplier’s release schedule, equipment somebody has to physically replace, and systems nobody had written down. The first two are not yours to shortcut. The third — knowing what cryptography you have, and being able to replace it from one place — is a decision an organization gets to make. That decision is crypto agility.

      Method

      How this model works

      Every number on the result screen comes from the eight steps below. Nothing is hidden, nothing is random, and the same choices always produce the same answer.

      1. Start from a fixed set of systems. Each industry is a group of named systems drawn on the picture. Every one of them sits in a layer — public edge, applications, network and VPN, identity and keys, or suppliers and old equipment — and says which kind of cryptography it relies on: key agreement, signatures, certificates, or symmetric encryption.
      2. Apply the readiness level you chose. It sets how much of each layer has already been upgraded. The suppliers and old equipment layer never goes above 15%, because physical equipment is not something a software rollout can fix.
      3. Work out what the organization can even see. The same logic decides which systems have been written down, with equipment out in the field counted as harder to find. This is the only place that is decided — and how centrally the organization can make changes deliberately does not affect it, because you cannot manage something nobody has recorded.
      4. Set off the event. Each one has its own rule for what it reaches. Q-Day hits anything still relying on public-key cryptography. A banned protocol hits the systems still using it. A flaw in a post-quantum product hits only the systems that already moved to it. A failed certificate authority hits everything that depended on it, upgraded or not.
      5. Sort every affected system into one of four outcomes. Not written down anywhere, so nothing reaches it. Physical or too old to change, so blocked no matter what the policy says. Waiting on a supplier who has not shipped a fix yet, so also blocked. Everything else is work the organization can actually get on with.
      6. Follow the knock-on effects one step. Anything directly connected to an affected system becomes less trustworthy too. It does not automatically fail — treating it that way would turn one broken system into a broken organization, and that is not how dependencies behave.
      7. Add up the work. Each system that can be reached costs time to change, plus time spent finding the owner and agreeing the change. More people help, but not proportionally. Central control removes up to 55% of the changing and up to 85% of the chasing — the chasing is what crypto agility is really for.
      8. Compare fairly. The fragmented figure is exactly the same organization with central control set to zero. Industry, event, suppliers, records and people are identical on both sides, so the difference between the two bars can only come from one thing.

      What this model cannot tell you

      • It is not a probability. Nothing here is a likelihood, an expected loss, or a risk score. The figures compare assumptions you chose against each other.
      • It does not predict Q-Day. The event horizon is the window over which traffic is assumed to be captured — not a forecast of when anything happens.
      • These systems are stand-ins. Nine to eleven named systems stand for whole categories, not a list of anything real. An actual organization has thousands, so the proportions matter and the counts do not.
      • The day counts are illustrative. How long a system takes, how much central control helps, and when each supplier ships are all assumptions written into the model, not measurements. Change them and every number changes.
      • Dependencies are simplified. Knock-on effects travel exactly one step, along a small set of connections drawn by hand. Real ones are far larger, loop back on themselves, and are partly unknown even to the organization.
      • It says nothing about your organization. This is a thinking tool for reasoning about crypto agility. It is not an assessment, an audit, or advice.

      A deterministic tabletop model: the same choices always give the same answer. The figures compare assumptions you selected against each other — they are not breach probabilities, loss estimates, or a forecast of when Q-Day will happen. Nothing you enter leaves this browser.
