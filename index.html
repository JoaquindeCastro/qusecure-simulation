      Method

      How this model works

      Every number on the result screen comes from the steps below. There is no hidden weighting and no randomness — the same inputs always produce the same output.

      1. Start from a fixed estate. Each industry is a set of named systems drawn on the illustration. Every system belongs to one band — public edge, applications, network and VPN, identity and keys, or vendor and legacy — and declares which cryptography it depends on: key agreement, signatures, certificates, or symmetric encryption.
      2. Apply the readiness level. The chosen level says what share of each band has already migrated. The vendor and legacy band never exceeds 15%, because hardware and unsupported equipment are not a software problem.
      3. Apply inventory visibility. The same share logic decides which systems the organization can see, with embedded and field equipment discounted further. This is the only place discovery is decided, and orchestration is deliberately not an input to it.
      4. Fire the event. Each event has its own rule for what it touches. Q-Day hits anything relying on public-key cryptography that has not migrated. A protocol deprecation hits systems still speaking the old protocol. A PQC implementation flaw hits only systems that already migrated. A trust-chain failure hits everything depending on certificates, migrated or not.
      5. Classify every affected system. Not catalogued → nothing reaches it. Hardware or unsupported → blocked, whatever the policy says. Vendor-dependent below that supplier's readiness gate → blocked. Everything else → work the response can actually do.
      6. Spread reduced assurance one hop. A neighbour of an affected system loses assurance. It does not automatically fail — that would turn one broken system into a whole broken enterprise, which is not how dependency works.
      7. Cost the work. Each reachable system carries change effort plus coordination effort, weighted by band. Teams divide it with mild diminishing returns. Orchestration removes up to 55% of the change effort and up to 85% of the coordination — coordination is the part crypto agility is actually for.
      8. Hold everything else constant. The fragmented figure is the same estate with orchestration at zero. Industry, event, vendor readiness, inventory and team capacity are identical on both sides, so the gap is attributable to orchestration alone.

      What this model cannot tell you

      • It is not a probability. Nothing here is a likelihood, an expected loss, or a risk score. The figures compare assumptions you chose against each other.
      • It does not predict Q-Day. The event horizon is the window over which traffic is assumed to be captured — not a forecast of when anything happens.
      • The estate is a stand-in. Nine to eleven named systems represent classes of system, not an inventory of a real organization. A real estate has thousands, and the ratios matter more than the counts.
      • Effort figures are illustrative. Days per system, the agility ceilings and the supplier gates are stated assumptions, not measurements. Change them and every number moves.
      • Dependencies are simplified. Assurance spreads exactly one hop along a small hand-drawn graph. Real dependency graphs are larger, cyclical, and partly unknown.
      • It says nothing about your organization. This is a tabletop instrument for reasoning about crypto agility. It is not an assessment, an audit, or advice.
